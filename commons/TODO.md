## Comparable-API comparison — commons gaps (2026-08-14)

*Audited `commons/{chat/placeholder,text,gui,player,command}` against a comparable dev API's module structure (Pixelmon-Reforged-scoped, comparison point only, not a port/copy source), reading real source on both sides rather than comparing directory names.*

### Structural gaps (worth considering, not urgent)

- [x] ~~**`PlaceholderManager.replace()`** — single-line `String -> String` only, a provider can't expand into multiple lines.~~ **Fixed 2026-08-14:** added `chat/placeholder/MultiLinePlaceholderProvider.kt` (opt-in `PlaceholderProvider` extension) and `PlaceholderManager.replaceLines(player, lines)` — expands a line that is *entirely* a single placeholder token (e.g. `"%player_stats%"`) into however many lines its provider returns; every other line, including inline placeholders mixed into a larger line, still goes through the existing single-line `replace`. Existing `PlaceholderProvider` implementors are untouched (additive, not a breaking interface change). Also fixed `providers` from a plain `mutableMapOf` to `ConcurrentHashMap` — `register()` can be called from multiple platform init paths while `replace()`/`replaceLines()` are already being read from on the command/chat thread, the same unsynchronized-map bug already fixed elsewhere in this file for `InjectorRegistry`/`TabRegistry`.
- [x] ~~**`ChatPaginator`** — pagination fused directly to `LuxPlayer.sendMessage`, no way to get page content as `List<String>` for other surfaces.~~ **Fixed 2026-08-14:** split page computation into `getPageLines(pageNumber): List<String>` (header + item lines, or the empty-state line) and `getFooterLine(pageNumber): String` (the interactive MiniMessage footer), both usable standalone. `sendPage` is now a thin composition of the two (`getPageLines(...).forEach(player::sendMessage)` + one more `sendMessage` for the footer) — output is unchanged, verified by a test asserting `sendPage`'s sent messages equal `getPageLines(...) + getFooterLine(...)`.
- [x] ~~**`GuiBuilder`** — items are placed once at build time, no per-pane tick/animation hook.~~ **Fixed 2026-08-15:** added `GuiBuilder.setAnimatedItem(slot, period, initialDelay = period, async = false, supplier)`, which seeds the slot immediately and, once the builder's `build()` calls the new `protected startAnimations(gui)`, schedules a repeating `LuxScheduler` task that calls `gui.setItem(slot, supplier())` + `gui.refreshAll()` each tick. The task self-cancels via `Gui.hasViewers()` once nobody's watching, so a closed GUI's animation doesn't run forever. This item turned out bigger than the other two in this section, as scoped on 2026-08-14: `Gui` had no viewer-tracking (`open`/`close`/`refresh` all took an explicit `player`), so `Gui.refreshAll()`/`Gui.hasViewers()` were added to the interface, and every platform had to implement them — `FabricGui`/`NeoForgeGui` each gained a hand-tracked `viewers: MutableSet<ServerPlayer>` (vanilla gives no reverse lookup from a container back to its viewers), kept accurate by overriding `LuxMenu`/`NeoForgeMenu.removed(player)` for client-initiated closes (ESC, inventory swap, disconnect) in addition to `close()`; `BukkitGui` needed no tracking at all — `Inventory.getViewers()` is already authoritative. `startAnimations(gui)` is wired into all six concrete builders (`Fabric`/`NeoForge`/`Bukkit` × plain and `Paginated`), since `PaginatedGuiBuilder extends GuiBuilder` and would otherwise silently accept `setAnimatedItem` calls that never start.
- [x] ~~No offline-player name-to-UUID resolution.~~ **Fixed 2026-08-14:** added `player/PlayerLookupService.kt` (interface) and `player/InMemoryPlayerLookupService.kt` (default, `ConcurrentHashMap`-backed, case-insensitive, in-process only). New `player/OfflinePlayer.kt` data class plus `command/injector/impl/OfflinePlayerInjector.kt` resolve a name to a UUID whether or not the target is online, checked via `PlayerManager` first, falling back to the lookup cache. `PlayerInjector` now optionally records successful online resolutions into the same cache so later offline lookups can find them. Wired into `fabric`/`neoforge`'s `LuxFabricInitializer`/`LuxNeoForgeInitializer` (`InjectorRegistry.registerOfflinePlayerInjector`) — Bukkit untouched, it already resolves offline players via Bukkit's own `OfflinePlayer` API. **Known limitation, by design for this pass:** the cache only remembers players referenced in a command since server start; it does not persist across restarts and isn't populated on join. A persistence-backed `PlayerLookupService` (e.g. via the `database` module) can be registered in its place through the same `InjectorRegistry` call without any interface changes — not done here, no evidence of a concrete need yet.

### Minor DX gap (low priority)

- [x] ~~Tab-completion requires a dedicated `TabHandler` per command.~~ **Fixed 2026-08-14:** added `command/injector/CompletingInjector.kt` — an opt-in `ArgumentInjector` extension with `getSuggestions(sender, args, index)`, same `index` convention as `instantiate`. `CommandProcessor.getParameterSuggestions` now falls back to it (`command/CommandProcessor.kt:221-225`) after the existing `@TabComplete` annotation and `TabRegistry` checks, so precedence is unchanged for anyone already using those. `PlayerInjector` and `OfflinePlayerInjector` both now implement it (suggests online player names, prefix-filtered) — this was a real, demonstrable gap, not hypothetical: `LuxPlayer::class.java` was never registered in `TabRegistry` anywhere in the repo, so any command taking a `LuxPlayer` parameter got zero tab-completion before this. Also removed `CommandProcessor.kt`'s old `targetParam == LuxPlayer::class.java` special-case block — it was unreachable dead code, checking the exact same `TabRegistry` lookup already performed one line above it.
